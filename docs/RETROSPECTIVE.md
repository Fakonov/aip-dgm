# 复盘：把一台 1997 年的 4-bit 掌机塞进 ESP32

> 项目：Digital Monster（数码暴龙机）V1 原版固件 → FoloToy AI Passport（ESP32-C3）
> 周期：2026-10-31 → 2026-11-04，65 轮迭代，v1.0 发布
> 本文不记流水账。流水账在 `PROGRESS.md`（1964 行，逐轮带真机日志）；
> 这里只写**能搬到下一个项目去的东西**。

---

## 0. 一页速览

| 项 | 值 |
|---|---|
| 代码量 | 固件 ~150 KB 源码（核心 2,675 行 C99 + 应用 2,525 行）；主机探针 30+ 个 |
| 文档量 | 14 万字（PROGRESS 6.1 万 + 交接单 2.3 万 + 其余） |
| 真机刷写 | 20+ 次，每次都核对 `Wrote N bytes` 与构建产物 |
| 核心正确性 | 50 万步逐位对齐参考实现，`pc trace sha256: f42d1802…` |
| 行为数据 | 进化规则跑遍 14,112 组养育条件，压成 12 条区间规则并逐行回放 |
| 最终产物 | 固件 880,768 B / 单文件控制台 242 KB / 三 ROM / v1.0 双交付包 |
| 代码来源 | ROM 是 Bandai 的，**不进仓库**；核心移植自 CC0 的 BrickEmuPy |

一句话：**这不是"写个模拟器"，是"用实验把一台没有文档的机器逼供出完整规格，再把它搬到另一块硅片上"**。
方法论的比重远大于编码。

## 1. 项目是怎么走过来的

七个阶段，每个阶段的"手段"和"代价"才是可复用的部分。

### 阶段 1：先证明这件事可行（round 1–3）

- **要回答的问题**：Python 参考实现跑这 ROM 有多快？够不够实时？
- **手段**：跑 BrickEmuPy 核心，实测 86k 指令/秒；实时需要 151k → **必须 C 移植**
- **结论**：可行性用数字锁死，不是"应该能行"
- **代价**：半天。省下的是一周后才发现方向错误的代价

> 迁移用法：**动手前先用一个下午算出"这个方案的天花板在哪"**。这里的数字（86k vs 151k）
> 直接决定了后面两周的工作形态。

### 阶段 2：把显示系统逆向出来（round 4–9）

- **要回答的问题**：32×16 的 LCD 是帧缓冲还是段驱动？
- **手段**：解析 `.brick` 设备描述与 `DigimonV1J.svg`，把段 id 光栅化成 32×16 位图表，
  生成 `digimon_segmap.h`（520 个段 = 512 点阵 + 8 图标）
- **结论**：**段驱动**。这意味着"画图"不是写像素，而是按段表组装字节
- **代价**：段表生成脚本 + 一轮比对渲染

### 阶段 3：位精确移植（round 10–33）

- **要回答的问题**：C 版和 Python 版是不是同一条机器？
- **手段**：
  1. 先跑通 Python 参考，产出**黄金轨迹**（50 万个时钟点的 PC/VRAM 哈希）
  2. 逐条指令翻译，每 5 万步比对一次 `instr / pc / vram[169]`
  3. 不一致就二分定位到具体指令
- **结论**：`ALL CHECKPOINTS MATCH` + 单一 `pc_trace_sha256` 作为回归指纹
- **代价**：这是最枯燥也最值钱的一段——**后面所有调试都建立在"核心不会骗我"之上**

> 迁移用法：任何"移植/重写既有系统"的任务，先造一个**逐点可比的黄金轨迹**，
> 再把"是否一致"变成一个字符串比较。从此每次改动都有免费回归。

### 阶段 4：上板（round 34–46）

- 编译、分区、LVGL、无 PSRAM 的帧缓冲预算、音频、按键 ADC
- **代价最大的教训**：帧预算按"固定步数"算是错的，必须按 OSC1 tick 计量
  （固定 8300 步/帧 → 时间 4 倍速；改 655 tick/20 ms → 误差 0.3%）

### 阶段 5：视觉还原（round 47–57）

- 按真机玻璃**像素实测**重排版式（一块玻璃三条带、32:28.7、pitch 7）
- 三次推翻自己的结论：图标先是"丝印"（round 39）→ 再是"ROM 驱动的段"（round 47）
- **结论**：屏幕上的一切都由 ROM 驱动，固件只做"读段位、画描边或实心"

### 阶段 6：产品化（round 58–62）

- 设置菜单、存档、PLAY TIME、SKIP TIME、ROM 二级槽位、重置存档
- 这一阶段暴露的 bug 几乎全是**交互语义**而非算法：长按被 BSP 事件打断、
  半透明面板叠半透明全是残影、NVS 提交造成"慢动作收起"

### 阶段 7：工具链与对外（round 63–65）

- PC 控制台（单文件 Web Serial）、串口数据面、连接自检
- 把"诊断"做成产品功能：`STATE / AGES / RAM / DUMP` + 一键自检
- v1.0：剥离版权素材、纠正许可证、双交付包

## 2. 十条可复用的方法论

### ① 先建"可证伪的事实表"，再动手

项目开头就有一张表：MCU 型号、时钟、ROM 大小、显示类型、按键 mask、声音位。
每条都标注**来源**（产品规格 / 引脚定义 / BSP / 手册 / README），冲突时按优先级裁决。

> 迁移：新硬件项目第一步不是写代码，是**列一张"我以为的事实"表并给每条找出处**。
> 表里没出处的条目，就是后面会炸的地方。

### ② 分层验证阶梯：主机 → 仿真 → 真机，别跳级

| 层 | 能验证什么 | 不能验证什么 | 成本 |
|---|---|---|---|
| 主机探针（`src/probe_*.c`） | 核心行为、RAM 映射、页面内容 | 显示时序、按键电气 | 秒级 |
| 官方模拟器（WASM） | 固件启动、菜单流程、截图 | USB 串口、真实按键手感 | 分钟级 |
| 真机 | 一切 | —— | 每次要刷写 + 人眼 |

**本项目最赚钱的习惯**：能在主机上复现的问题绝不上真机。
第 65 轮那个"体重 91 vs 20"的 bug，全过程没碰真机——导出一份存档、
在主机上把 ROM 的页面逐页打印出来、做因果扫描，两小时结案。

> 迁移：把"上机"当成昂贵操作。**先问"这能不能在主机上复现"**，
> 能就不要刷机。真机只用来验证"只有真机才有的东西"。

### ③ 移植要有黄金轨迹和一个哈希

不是"看起来对"，而是 `f42d1802…` 完全相等。有了它：
- 改核心 → 跑 30 秒知道有没有破坏行为
- 别人接手 → 一条命令确认环境没坏
- 发布 → 写进 CHANGELOG 当契约

> 迁移：任何重写/移植，先造**确定性的黄金输出**（哈希、快照、逐点数据），
> 再把回归成本压到"跑一次 + 看一眼"。

### ④ 判据是"精确等于"时，必须专门做边界测试

ROM 的进化判定比较四个 nibble 全等才触发；**跨过那一分钟就永久丢失**。
这种"等号型"判据在排程、定时器、状态机里到处都是，而它最容易被
"停在 next-2 / next+5"这种拙劣测试漏掉。

本项目的做法：写 `src/evo_probe.c`，A 组停在 `next−2`（必须进化）、
B 组停在 `next+5`（必须不进化），变成一条可重复的断言。

> 迁移：把"边界"写成**成对的断言**（刚好内 / 刚好外），而不是靠人工试。

### ⑤ 用因果实验代替读代码

要回答"屏幕上那个 91 来自哪个 RAM 字节"，有两条路：
读 8,000 条反汇编，或者**把每个 nibble 逐个 +1 再重画同一页**，看哪一位能改变画面。

后者的实现只有 80 行（`src/probe_causal.c`），跑完直接给出因果表：
`M(56)/M(57)` 是体重，`M(68)/M(69)` 根本没参与绘制。

> 迁移：黑盒系统定位字段时，**扰动一个变量、观察输出**比读代码快一个数量级。
> 前提是你能把系统放进可重复的沙盒（这里靠"存档 → 主机复现"）。

### ⑥ 语义陷阱：同名不同物

`M(68-69)` 在 RAM 图里叫 `base_weight`（种族基准体重，进化时写一次），
而玩家看到的体重在 `M(56)/M(57)`。两者的差值是"喂了多少"。

工具读错地址 → 用户看到 20 而不是 91。**两个数都是真的，只是答的不是同一个问题。**

> 迁移：文档里的字段名是**别人的命名**，不是你的语义。落地前用一次实验确认
> "这个值在界面上对应哪个数字"。

### ⑦ 版本纪律：产物指纹 + 刷写核对

- 每次交付记 `版本号 / 字节数 / SHA256 前 16 位 / 时间`
- 刷机后核对 `Wrote N bytes` 是否等于构建产物
- 曾经"编译成功但没刷"，排查了一整轮才发现设备跑的是旧固件

> 迁移：**"我改了" 和 "它生效了" 是两件事**，中间必须有一次字节数或哈希的核对。

### ⑧ 文档即跨会话记忆

65 轮跨了多个会话，其中一半的结论是"上一轮写在文档里的"。
`PROGRESS.md` 记流水与数据，`HANDOFF.md` 记"新会话先读什么"+ 坑清单，
每次会话结束前更新后者。

> 迁移：给长项目定一个**两文件约定**：
> 一份只增不改的历史（可检索），一份永远是最新的入口（可执行）。
> 入口文件里最重要的是"别重踩的坑"，不是"我们做了什么"。

### ⑨ 把诊断做成产品功能

不是"出问题再临时写脚本"，而是让固件自带 `STATE / AGES / RAM / DUMP`，
让工具自带「连接自检」（逐条发命令、逐条报 OK/NO REPLY）。

第 64 轮就是靠自检一眼看出：`ROMINFO OK / DUMP OK / PET OK`，而
`STATE / AGES / RAM` 全 NO REPLY —— 指向性极强，直接锁定"新加的三条命令没在跑"。

> 迁移：给系统装一套**结构化自检**，让"哪一层坏了"这个问题有工具回答，
> 而不是靠人猜。

### ⑩ 交付物分档，别混在一起

| 档 | 用途 | 内容 |
|---|---|---|
| 里程碑快照 | 回滚 | 源码 + 产物，冻结不动 |
| 交付包 | 给人用 | 固件 + 工具 + 说明书 + 校验 |
| 公开仓库 | 发布 | 源码 + 文档，**剥离版权素材**，路径通用化 |

v1.0 时把三者分开，并且发现：公开树里那份控制台必须**去掉内嵌的扫描图**
（237 KB → 66 KB），否则等于把别人的版权素材一起发布。

> 迁移：发布前跑一遍"这个文件里有别人的东西吗 / 有我的隐私路径吗"的机械检查。

## 4. 坑的分类学

三十多条坑按层归类，比逐条罗列更有用——新项目踩的往往是同一类。

### 4.1 电气 / 硬件层
- 电源键是**硬件闩锁**，没接 MCU → 固件永远读不到，不能拿来做功能
- ADC 阶梯键盘三键共用一脚 → **无法识别同时按下**，长按不稳会串键
- 按键扫描 2 Hz，**按不足 120 ms 直接丢**；固件要把按下垫到 260 ms
- UART0 TX 与背光抢同一个 GPIO → 真机只能用 USB-Serial-JTAG 做控制台

> 教训：**先读引脚定义，再设计交互**。所有"软件能不能做"的问题，答案在电气图里。

### 4.2 驱动 / RTOS 层
- BSP 除 PRESS/RELEASE 还会上报 CLICK/DOUBLE/**LONG(500 ms)**；
  把非 PRESS 当松手，长按永远到不了 1.2 s
- LVGL 不是线程安全的：非 LVGL 任务改 UI 必须持锁（曾导致切配色死机）
- 30 px 圆角遮罩对每次 flush 生效 → 四角 30 px 内会被切掉

### 4.3 资源 / 内存层
- 无 PSRAM 时**最大连续堆**才是硬约束：pitch 8 需要 118 KB，初始化后只剩 112 KB → 只能 pitch 7
- 颜色常量：`lv_color_hex()` 吃 RGB888，画布缓冲是 RGB565 —— 混用会把边框画成亮蓝

> 教训：内存问题要算**最大连续块**，不是总量；颜色问题要写清"这个变量是哪种编码"。

### 4.4 编码 / 数据语义层
- **BCD vs 二进制混排**：阶段时间的小时是 8-bit 二进制，只有分钟是 BCD
- **"精确等于"型判据**跨过即永久丢失
- 同一概念两个字段：基准体重 vs 当前体重
- 存档 blob 是 32 位 ABI 布局，换到 64 位主机要整体平移 4 字节

> 教训：**每个字段都问一句"这是怎么编码的、谁写的、谁读的"**，
> 三问答不上来就先做实验。

### 4.5 工具链 / 流程层
- `idf.py build` **不重建**合并镜像 → 仿真悄悄跑旧镜像
- 分区表被注释吞掉 → 构建用的是 IDF 自带表，项目里的 csv 形同虚设
- 编译成功 ≠ 刷进去了；刷机命令跑的是上一个产物
- PowerShell 5.1 按 ANSI 读 UTF-8，`-replace` 回写会**不可逆毁掉中文**

> 教训：**构建产物的时间戳和大小要肉眼核一次**；改文本一律用能保编码的工具。

### 4.6 前端层
- `forEach` 里写 `continue` 是语法错误 → 整段 `<script>` 静默不执行
  （页面照常渲染、按钮全哑、`?demo=1` 不载入，极像"初始化失败"）
- `ResizeObserver` 盯 `body` + 回调里改 SVG 尺寸 = 自激死循环，主线程锁死
- 串口断开顺序错（先 cancel 再清 port）→ 读循环重挂 reader，`close()` 永久等锁
- headless 截图的 DPI 会骗人：量尺寸要用 `--dump-dom` 读 `getBoundingClientRect()`

> 教训：前端 bug 的**症状和原因通常不在同一层**。JS 改完先 `node --check`，
> 再看 DOM，最后才截图。

## 5. 走弯路的复盘

| 弯路 | 花了多久 | 根因 | 正确做法（当时就该做的） |
|---|---|---|---|
| 图标"是丝印不是段" | 8 轮 | 探针停在 mode 1，从没进过 mode 2..8 | 探针要覆盖**状态机的全部状态**，不能只测"我觉得会走的那条路" |
| "进化不触发" | 1 整轮 | 把二进制小时当 BCD 解码，显示成 26:23 而实际 20:23 | 先验证**诊断工具本身**，再怀疑被测对象 |
| pitch 8 调了半天 | 半天 | 只算总量不算最大连续块 | 内存问题先打印 `heap_caps_get_largest_free_block` |
| "STATE 无响应" | 半轮 | 编译了但没刷 | 刷机后核字节数，写进流程 |
| 网页端体重 20 | 半轮 | 字段语义错（基准 vs 当前） | 拿一次真机屏幕的数和 RAM 对照 |

**共同模式**：所有弯路都不是"想不到"，而是**没验证前提**。
所以第 6 节的清单，本质是"开动前必须验证的前提"。

## 6. 新项目开工清单

给"把老硬件/老固件搬到新板子上"这类任务用。

**第 0 天：情报**
- [ ] 列出"我以为的事实"表，每条写出处；没出处的标记为待验证
- [ ] 找到至少一份**独立参考**（模拟器 / 反汇编 / 别人的移植），并确认其许可证
- [ ] 算一次性能天花板：目标帧率需要多少指令/秒，候选方案能给多少

**第 1–3 天：可在主机上验证的最小闭环**
- [ ] 参考实现能在主机跑通，并有确定性输出（哈希/快照）
- [ ] 写第一个探针：能读状态、能单步、能打印画面
- [ ] 建立"改一次 → 跑一次 → 30 秒内知道对错"的循环

**移植期**
- [ ] 黄金轨迹 + 逐检查点比对（不是"看着像"）
- [ ] 核心与平台解耦（无 malloc、无平台头文件），主机和固件共用同一份

**上板期**
- [ ] 计时按**硬件时钟 tick** 计量，不按循环次数
- [ ] 内存：最大连续块 > 需求的 1.3 倍
- [ ] 每个外设先跑一个最小验证，再集成

**产品化期**
- [ ] 结构化自检（一条命令问出"哪层坏了"）
- [ ] 版本号 + 产物哈希 + 刷写核对，写进发布流程
- [ ] 交付物分三档（快照 / 交付包 / 公开仓库）

**发布前**
- [ ] 机械检查：有没有别人的版权素材？有没有个人绝对路径？
- [ ] 许可证核对到**上游仓库原文**，不要抄二手说法
- [ ] 公开版能否独立构建/运行（不能依赖你本地才有的东西）

## 7. 关键数字（备查）

| 数字 | 含义 |
|---|---|
| 50 万步 | 核心比对的步数，10 个检查点 |

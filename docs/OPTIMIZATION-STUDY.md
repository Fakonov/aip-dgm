## 0. 核实：真机内模拟对战对 V2/V3/V4 是否生效

**结论：全部生效，四个 ROM 一视同仁。**

做法：拿 `src/card_test.c`（主机版卡片对手，逻辑与固件 `dg_cards.c` 同源）分别对四个 ROM 跑完整四帧：

| ROM | 文件 / CRC | 帧 1（真机的卡） | 卡片回帧 | 帧 2（真机判定） | 卡片回帧 | 结果 |
|---|---|---|---|---|---|---|
| V1 | `digimon.bin` / `08ffac1b` | `3FC0` data `03` | `A35C` data `3A` | `BF40` data **`02`** | `7788` data `11` | **PASS** `bouts 0→1` |
| V2 | `digimonv2.bin` / `19a9e54e` | `3FC0` data `03` | `A35C` data `3A` | `B748` data **`12`** | `7788` data `11` | **PASS** `bouts 0→1` |
| V3 | `digimonv3.bin` / `3000cf30` | `3FC0` data `03` | `A35C` data `3A` | `BB44` data **`22`** | `7788` data `11` | **PASS** `bouts 0→1` |
| V4 | `DigimonV4J.bin` / `27df4fd6` | `3FC0` data `03` | `A35C` data `3A` | `B34C` data **`32`** | `7788` data `11` | **PASS** `bouts 0→1` |

**唯一的版本差异**：帧 2 的高 nibble 是 **ROM 自己的版本号**（V1=0 … V4=3），低 nibble 是胜负。
卡片回的版本号（测试里固定回 1）**不影响结果**——四个 ROM 都接受了 —— 这和 DMComm 的
「V1 当受方时鹦鹉学舌回对方的 version」对得上。所以：

- 网页端写卡时填 `version` 只是为了记录来源，**换 ROM 打也不会失效**（已实测跨版本接受）
- 真机上 V2/V3/V4 槽位跑卡片对战不需要任何额外适配

> 这一条是真的跑了四遍主机测试，不是推断。原始输出见 `PROGRESS.md` 本轮记录。

## 1. 运行效率与耗电

### 1.1 先看实测账本

| 指标 | 数值 | 来源 |
|---|---|---|
| 每帧 ROM 模拟量 | 8300 次 `clock`/`dg_step`，677,365 条指令 | 实测 `src/bench.exe` |
| 跳过时的吞吐 | 2 H 游戏时间 = **150 s 墙钟** ≈ **48× 实时** | 实测（HANDOFF round 62 的 2H 跳过） |
| 反推每帧模拟耗时 | 20 ms ÷ 48 ≈ **0.42 ms**，占 20 ms 预算 **≈ 2 %** | 推算 |
| 渲染耗时 | `avg_us=1471 / max_us=1496` 每次重绘 | 实测（仿真 `DIAG`） |
| 实际重绘频率 | 500 帧里只有 **11 次**（2.2 %） | 实测（仿真 `DIAG`） |
| 空闲堆 | 104,908 B（仿真），最大连续块 40,960 B | 实测 `DIAG` |
| CPU 频率 | **160 MHz**（不是 240） | `sdkconfig` `CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ=160` |
| 编译优化 | `-O2`（`PERF`），Flash **DIO** 模式 | `sdkconfig` |

**结论先行：ROM 模拟只吃掉 2 % 的 CPU，剩下 98 % 是 `vTaskDelayUntil` 睡掉或 LVGL 任务空转。**
所以"跑模拟本身费电"这个假设不成立，**省电空间在别处**。

### 1.2 逐条回答你的问题

**Q：连着 PC 时，真机上是不是一直在跑端口监听？**

是，但**几乎不花 CPU**：`console_poll()` 每帧最多读 32 字节（`con_getc()` 内是
`usb_serial_jtag_read_bytes(..., 0)` 非阻塞读），空转成本约每帧几微秒。

真正的成本不在这里，而在 **USB-Serial-JTAG 外设常开**：它挂着 48 MHz 时钟、常驻中断。

> **2026-11-08 更新（round 97/98 / todo #15）**：试过了，**功能已整体移除**。
> 结论三条：① 能关掉的是 PHY pad + USJ 中断，推算只省 **1–2 mA（占整机 2–4%）**，
> 因为总线时钟关不掉 —— `usb_serial_jtag_connection_monitor.c` 注册的 FreeRTOS tick hook
> 每 tick 读 `USB_SERIAL_JTAG.int_raw` 清 SOF，而 `esp_register_freertos_tick_hook` 没有反注册接口；
> ② pad 关掉是**单向门**：`phy_enable_pad(true)`、外设复位、`esp_restart()` 都救不回来，只有按电源键断电；
> ③ 对 #4 的价值不需要用户开关 —— 浅睡本来就会断 USB，要浅睡就在流程里静默关。
> 对比一下：背光 100%→70% 就是 6–12 mA，是它的 5–10 倍，**省电清单上这项不值得排**。
> 三轮实测记录在 `docs/HANDOFF.md` 的「已放弃：#15」。

**Q：8 个 ROM 槽位减少几个，能不能优化运行效率？**

**不能，运行时零收益。** 槽位表是 `dg_rom_entry_t s_roms[8]`（约 8×40 B = 320 B 静态 RAM），
开机 `ROM_INFO` 读一次就完了；运行时只有 `s_rom_idx` 一个下标在使用。
减到 4 个只省 **不到 200 B**，还会丢掉"四个 ROM 各一份存档"的便利。**不建议改。**

**Q：ROM 累计游玩时间的计时会不会加大耗电？**

**不会。** `age_tick()` 每帧做一次整数比较 + 加法（`s_age_frac` 累加 20 ms），
每秒落盘一次 NVS（`nvs_set_u32` + `nvs_commit`）。真正有成本的是**存档写入**：

- 每 60 s 一次滚动存档（`save_slot()`，约 1.3 KB 写入 + commit），每次阻塞 ~100 ms
- 对战结束 `bouts` 变化后 1.5 s 再存一次
- **可以考虑**：把存档周期从 60 s 拉到 5 min（减少 flash 擦写和 100 ms 的卡顿），
  代价是掉电丢的时间从 1 min 变成 5 min。这个由你定。

**Q：那真正的耗电大头在哪？**

| 项 | 量级 | 能不能动 |
|---|---|---|
| **LCD 背光 LED** | 通常 20–40 mA，占整机一半以上 | 菜单已有 `BRIGHT` 20–100 %；**自动熄屏**已实现（`AUTO OFF`）。这是最有效的省电开关 |
| ESP32-C3 CPU | 160 MHz 常跑 **20 mA**；80 MHz **15 mA**（手册 Modem-sleep 表） | ✅ **可开动态调频**（见下） |
| LCD SPI 刷新 | 每次全玻璃重绘 192×183×2 = 70 KB @ 40 MHz ≈ 14 ms | 已有脏检测，平均 2 % 帧才刷 |
| 音频 | I2S 常开 + 320 样本/20 ms | 静音时可以不喂数据（现在仍每帧喂 0，可改成"没声音就停 I2S"） |

### 1.3 建议（按性价比排序）

| 优先级 | 措施 | 预期收益 | 风险 / 成本 |
|---|---|---|---|
| **P1** | 打开 `CONFIG_PM_ENABLE` + `esp_pm_configure({max=160, min=40, light_sleep_enable=true})` | 空闲时自动降频/浅睡；手册口径 160→80 MHz 就有 **5 mA** 差；浅睡再低一个量级 | 中。要确认 I2S/SPI 与 light-sleep 的兼容性，可能出现音频断续。**必须真机长测** |
| **P2** | 静音时停 I2S（`fill_audio` 已能判断 `f<20`） | 省 I2S + 功放静态电流 | 低 |
| **P3** | 默认背光从 100 % 降到 70–80 % | 直接砍背光电流 20–30 % | 无风险，观感可接受 |
| **P4** | 存档周期 60 s → 5 min | 少 80 % 的 flash 写入 | 低，但掉电丢得更多 |
| P5 | `-O3` + `LTO` + Flash **QIO** | 模拟吞吐 +20–40 %（对跳过有用，对常态无感） | 低。QIO 需要 flash 支持，写盘速度也会变 |

> **不建议**：常态降频到 80 MHz。当前 160 MHz 下只剩 48× 的余量，80 MHz 会掉到 24×，
> ROM 时序虽然按 OSC1 计数不受影响，但帧率会不稳（20 ms 预算里 0.42→0.84 ms 还行，
> 主要是 LVGL 与音频抢占时容易掉帧）。用 P1 的动态调频代替。

## 2. 画面：能不能更好看，内存够不够

### 2.1 三套方案（效果图见 `docs/opt_compare.png`）

| 方案 | 做法 | 额外 RAM | 额外 Flash | 每帧成本 |
|---|---|---|---|---|
| **A 现状** | LVGL 矢量：深灰壳 + 圆角凹槽 + 玻璃画布 | — | — | 基准 |
| **B 初代配色**（推荐） | 同样是矢量，但换成真机的**白机身 + 深红上下条 + 红色挂绳孔板 + 深色描边** | **0** | **0**（纯颜色常量 + 几个圆角矩形） | 与 A 相同 |
| **C 彩色点阵** | 把 `background_322x321_0028.png` 缩到玻璃区当底图，点亮像素叠深色 | 需要 1 张 192×183 的 RGB565 = **70,272 B**（或 RGB332 35 KB） | 压缩源 ~35 KB | 每帧重绘玻璃时要重贴底图 → **+2–3 ms/帧** |

**关键观察：你给的那批 `dtector_*` / `texture_bg_*` 都是竖版机身图**，
中间是方窗（高宽比 ≈ 1.0），而本机是 **320×240 横屏、玻璃 192×183 居中**。
把整张机身图硬塞进来只有两条路：**压扁变形**（试过，很丑）或**玻璃缩到 150×120**
（等于退化回 round 89 之前的观感）。所以真正能落地的做法是：

> **移植它的"配色和家具"，而不是整张照片。** 也就是方案 B：白身 + 红条 + 挂绳孔板 + 描边，
> 全部用 LVGL 的矩形/圆角/颜色画出来。观感接近真机，**零内存代价**。

如果一定要用位图（比如石纹底、金属高光），建议做成**小尺寸平铺纹理**（如 32×32 石纹 tile，
2 KB）用 LVGL 的 `image` 平铺，而不是整屏大图 —— 大图在无 PSRAM 的 C3 上每次重绘都要从
flash 读，得不偿失。

### 2.2 内存账（现在还剩多少）

| 项 | 数值 | 来源 |
|---|---|---|
| LVGL 池 | 总 29,232 B，**已用 77 %**，最大空块 5,772 B | 实测日志 `lvgl pool card picker` |
| 玻璃画布 | 70,272 B（RGB565 192×183） | 代码常量 |
| 空闲堆 | 104,908 B / 最大连续 40,960 B | 仿真 `DIAG` |
| app 分区余量 | 57 %（893,856 / 2,097,152 B） | 编译输出 |

**结论**：
- 方案 B 完全装得下（几个矩形而已），甚至不用调池
- 方案 C 也能做（画布已经在那儿了，只是把底色从纯色换成一张 RGB565 底图，
  再多 70 KB **堆**或放 flash 走 `lv_image`）——但**每帧重贴一次底图**

> ⚠️ 提醒：LVGL 池已经 77 %。**下一次往界面里加控件之前，先把它从 32 KB 提到 40 KB**
> （Wi-Fi 已删，堆不紧张），否则会重演 round 92 那次「按 B 就重启」。

### 2.3 建议

1. **先做 B**（零成本、观感提升最大），配色常量放进现有 `SHELLS[]` 表，菜单 `SHELL` 行就能切
2. 如果还想要"点阵背景"，建议做成 **2–3 种低对比度底纹**（点阵网格的深浅、纸张质感），
   用 LVGL 的 `bg_image` + 小 tile，而不是整幅彩色插画
3. 图标贴图（56×28 × 16 张）现在是烘焙的，已经很好；**不建议**再加大

## 3. 跳过指定小时数 + 加快跳过

### 3.1 现状

- 菜单 `SKIP TIME`：OFF / 5M / 30M / 1H / 2H 五档，网页端可自定义 1–10080 分钟（最长 7 天）
- 实现是**真跑游戏时间**（`rom_skip_minutes()`：每批 8192 个 `dg_step`，每两批 yield 1 ms 刷进度）
- 实测速度 **≈ 48× 实时**（2 H 用 150 s）

也就是说，网页端现在**已经能跳 7 天**，只是要付出 7×24×60×60÷48 ≈ **3.5 小时**墙钟。所以问题不是"能不能"，是**太慢**。

### 3.2 能快多少

| 手段 | 预期加速 | 代价 |
|---|---|---|
| 跳过期间临时提频到 **240 MHz**（`esp_pm_configure` 或 `rtc_clk_cpu_freq_set`） | **×1.5** | 只在跳过这几十秒里耗电，平时不受影响 |
| `dg_step` 核心放 **IRAM**（`IRAM_ATTR`） | ×1.3–1.8（免 flash cache miss） | 约 10–20 KB IRAM，需实测 |
| `-O3` / `LTO` / Flash **QIO** | ×1.1–1.3 | 编译配置改动，需回归 |
| 跳过时**暂停 LVGL 任务**（现在它仍被周期唤醒） | ×1.02 | 边际，不建议为它动 BSP |
| 去掉 `vTaskDelay(1)` 的进度刷新（改成 5 % 一刷） | ×1.05 | 观感略差 |

**组合预期：48× → 90–110×**，即：

| 目标 | 现在 | 优化后（推算） |
|---|---|---|
| 2 H | 150 s | **70–80 s** |
| 24 H | 30 min | **14–16 min** |
| 7 天 | 3.5 h | **1.6–1.9 h** |

### 3.3 还有一个"作弊"选项（要不要，你定）

直接改 RAM 里的时间字段（`M(0x48..0x4F)` stage/next、`M(0x33)` 等）而不是真跑：
**瞬间完成**，但会跳过期间所有的饥饿 / 便便 / 进化命中 —— round 61 已经证明进化是
"某一分钟命中才进化"，硬改时间等于让宠物错过进化窗口。**我不建议**，除非明确接受"跳过期间不发生任何事件"。

### 3.4 建议

1. 菜单档位加 **12H / 24H**（现在最大 2H），网页端自定义已经支持
2. 先上 **跳过时提频到 240 MHz**（改动最小、收益确定）
3. IRAM 方案要实测 IRAM 余量，作为第二阶段

## 4. 网页端：简单 / 高级两种模式

### 4.1 现状问题

现在四页全摊开，一屏里 ROMIN/SAVEOUT/CRC/RAM/自检/帧表/原始命令全在，第一次打开容易懵。

### 4.2 建议设计（三级信息架构）

```
┌─────────────────────────────────────────────────────┐
│ 顶栏：连接设备 │ 模式开关 [简单 ● 高级] │ 日志      │
├─────────────────────────────────────────────────────┤
│ 简单模式只有三块：                                   │
│  ① 游戏卡带   —— 8 个槽的缩略卡，上传 / 启动         │
│  ② 我的数码兽 —— 当前形态 + 体重/年龄 + 进化倒计时   │
│  ③ 打一场     —— 卡片架 + 图鉴 + 「保存并开打」      │
│  （没有调试页、没有 CRC、没有帧表、没有原始命令）    │
├─────────────────────────────────────────────────────┤
│ 高级模式 = 现在的四页 + 全部调试件                   │
└─────────────────────────────────────────────────────┘
```

实现方式（成本可控）：

| 改动 | 工作量 |
|---|---|
| 顶栏加一个开关，`body.simple` 类控制 `display:none` | 1 小时 |
| 简单模式下把「对战」页只留离线卡片（隐藏电脑中继 tab） | 0.5 小时 |
| 简单模式默认隐藏日志栏、隐藏「调试」「养成」的折叠区 | 0.5 小时 |
| 文案瘦身：每块只留一句白话 + 一个主按钮（现在有些段落 3–4 行） | 2–3 小时 |
| 首次打开显示「三步上手」气泡，点「我知道了」永久记住 | 1 小时 |

**总计约 1 个工作日**，纯前端，不碰固件。

### 4.3 建议的"傻瓜化"具体动作

1. **默认进简单模式**，高级模式记在 `localStorage`
2. 每个按钮只留一个动词：`上传` / `启动` / `打一场` / `存下来`
3. 把「状态码语言」翻成人话：`ROMBAD` → 「这个文件不是 16 KB 的 ROM」；`武装成功` → 「准备好了，按设备上的 B」
4. 危险操作（擦 ROM、重置存档）在简单模式下**直接消失**，只在高级模式出现

## 6. 第一阶段实施记录（2026-11-07 23:0x 完成，未刷机）

### 6.1 做了什么

| 项 | 实现 |
|---|---|
| 新配色 `V1RED` | 白机身 `#F3F1E9` + 深红框 `#A81C1B` + 近黑凹槽 `#1C1C1C`，加进 `SHELLS[]`（第 15 项），菜单 `SHELL` 行能翻到，也可 `SHELLSET V1RED` 直接选 |
| 彩色点阵 `MATRIX 1` | 玻璃五种分块各取一个色：上图标带 8 槽 / 上间隙 32 列 / 点阵 32×16 / 下间隙 32 列 / 下带 8 槽，共 **592 个 RGB565 = 1.2 KB flash**（`main/dg_theme.h`），由 `tools/gen_theme_header.py` 从 `background_322x321_0028.png` 采样 |
| 图标透明 | `blit_slot()` 把**玻璃底色 `0x950D` 当色键**跳过，所以彩色主题下图标带不会又变回一条绿 |
| 开关持久化 | `MATRIX` 与 `shell` 一起存 NVS（键 `mtx`），重启保留 |

### 6.2 关于"那条绿色"

**你看到的绿色是预览图的合成 bug，不是固件行为**：玻璃在屏幕上是
`y = (240-183)/2 - 6 = 22`（`s_view_y` 特意上抬 6 px 给 HUD 让位），
我第一版效果图按 `y = 28` 贴的，于是玻璃底部 6 px 没被覆盖 —— 就是那条绿边。

但**固件里玻璃本身确实是绿的**（`GLASS_TONE` 三色橄榄），要"避免绿色"就得改渲染。
现在 `MATRIX 1` 下：

- 点阵格子：每格用 `dg_matrix_bg[r][c]`，格线是该色 ×3/4（`darken565()`）
- 上下图标带：每槽用 `dg_band_bg[band][slot]`
- 两条间隙：每列用 `dg_gap_bg[band][col]`

## 16. 真机反馈修正：图标"粘滞"（2026-11-08 01:0x，已刷 COM5）

**现象**：样式 C 下按 A 切到下一个功能图标，上一个图标的位置会整块变黑一会儿。

**根因**：`blit_slot()` 在样式 C 下遇到"玻璃底色"的像素直接 `continue`（跳过不写）。
这在**空画布**上是对的，但在**已经贴过上一张图**的画布上就错了 —— 被跳过的像素保留了
上一个图标的**点亮贴图（深色底板 + 白图案）**，于是失去高亮的那一格仍是深色块，
直到玻璃碰巧因为点阵变化整块重绘才恢复。

**修复**：跳过改成**写回背景** —— 遇到玻璃底色像素时，从 `dg_backdrop` 取该位置的颜色填回去，
每次贴图都完整覆盖，不再有残留。

```c
if (sv == DG_GLASS_KEY565) {
    dst[c] = dg_backdrop[dy * s_view_w + dx];   /* 原来这里是 continue */
    continue;
}
```

固件 `0x10FA60` = 1,112,672 B，已刷 COM5，`STATE` 存档完好。
